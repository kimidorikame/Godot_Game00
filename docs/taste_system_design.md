## 背景・動機

現状の味ステータスは `rich`（濃厚）/ `light`（あっさり）/ `umami`（旨味）の3軸（int）。

**問題**: `rich` と `light` は相反する概念なのに独立した2軸になっているため、「rich高かつ
light高」という味としてイメージできない矛盾状態が数値上は作れてしまう。軸設計の欠陥。

**方針**: 相反する概念は1軸の両端に統合し、矛盾を構造的に排除する。あわせて味の表現力を
上げるため軸を再構成する。

## 新しい4軸の定義

各軸は「1本のスライダー、両端に対義の味」。内部表現は単極（後述）。

| 軸 | 両端 | 内容 |
|---|---|---|
| コク | 濃厚 ⇔ さらり | 質感・口当たりの重さ。現 `rich`/`light` を1軸に統合 |
| 旨味 | 深み ⇔ 平坦 | 出汁の効き。現 `umami` を踏襲 |
| 刺激 | パンチ ⇔ マイルド | 塩気・辛み・スパイス。新設 |
| 香り | 芳醇 ⇔ 淡泊 | 香味野菜・ハーブの効き。新設 |

- 例: 濃い味スープ = 「コク:濃厚 旨味:深み 刺激:パンチ 香り:芳醇」
- 例: お湯に近い失敗作／病院食 = 「全軸が低い」

## 内部表現: 単極（案X）を採用

各軸は0以上の値。0=下端（さらり/平坦/マイルド/淡泊＝その味が無い）、値が大きいほど上端
（濃厚/深み/パンチ/芳醇）。お湯＝全軸ほぼ0。

- 双極（0=中央、負=さらり方向）は採用しない。理由: 表現したい「お湯=何も無い状態」は
  「全軸0」で素直に表せる。双極だとお湯が中央値になり直感に合わない
- 単極でも「さっぱり系の完成した味」は表現できる。評価は「値の高低」ではなく「客の
  `ideal` との距離」で決まるため、薄味好きの客は `ideal` が低い座標を指し、薄いスープ
  ほど距離が近く高評価になる（下記「評価の構造」参照）
- ※現状の型は int。レンジを大きく取って繊細な調整を可能にする案は別途「味スケールの
  解像度」課題として扱う（float化は採らない）

## 評価の構造: 2段構え

### 第1段（失敗判定・絶対ルール）

- 複数の軸が「薄すぎる」（お湯に近い）スープは、客の好みに関わらず低評価。「料理として
  成立していない」ことを表す
- 具体的な閾値（何軸未満を薄いとみなすか）と軸数（何軸以上が薄いと失敗か。相談では
  「3種以上」案が出た）は数値バランスであり、実装フェーズで要調整。仕組みとして存在
  することだけを今は確定する

### 第2段（好み評価）

- 第1段を通過した「成立しているスープ」を、客ごとの `ideal` との距離で評価。既存
  `Evaluator` の `distance_to`（attrs距離）を4軸に拡張して踏襲する
- 「濃すぎ」は絶対ルールに含めない。濃すぎるスープはそれを `ideal` とする客がいなければ
  全客の `ideal` から遠く、第2段の距離評価で自然に低評価になるため。上限を絶対ルールで
  縛る必要はなく、客の好み（`ideal`）調整で対応できる。薄すぎ（お湯）のみ非対称に絶対
  ルールで蓋をする

## 各軸を動かす手段（操作の割り当て）

軸を定義しても、それを動かす手段がなければ軸は機能しない。各軸の主担当を割り当てる。

- **コク**: ベースの濃さ ＋ 水を足す（下げる）／ベースを足す（上げる、将来仕様の
  `add_base` 相当）＋ 煮詰まり（煮込むと上がる）。操作手段が最も豊富。既存 `rich`/`light`
  の動きがここに集約される
- **旨味**: ベースの質 ＋ 鍋に入れる具材 ＋ 煮詰まり（煮込むほど出汁が出る）
- **刺激**: 薬味が主担当（辛み・塩気）。新設軸のため既存の薬味を刺激軸に紐付ける設計が
  必要
- **香り**: 香味野菜・ハーブ系が主担当。新設軸のため、香りを上げる食材の割り当て、また
  は新カテゴリ追加が必要になりうる

※刺激・香りは新設軸なので、それらを動かす食材が現状（トッピング3・薬味3）で足りるかの
棚卸しと、必要なら食材追加が実装フェーズの前提作業になる。

## 鍋レイヤーとカップレイヤーの非対称構造

味を作る場を2レイヤーに分け、各軸が動きやすいレイヤーを非対称に重み付けする。この非対称
は料理の物理から導かれる（ゲームルールではなく必然）。

- **鍋レイヤー**（量が多い・全客共通・営業前〜営業中にじわじわ育つ）: コク・旨味が大きく
  動く（煮込みで作る味）。刺激・香りは鍋に足しても量に薄まって効果が小さい
- **カップレイヤー**（一杯分・量が少ない・客ごとにサーブ時調整）: 刺激・香りが大きく
  動く（タバスコ、パクチー山盛りのように少量で効く）。コク・旨味は「煮ないと出ない」ため
  サーブ時には大きく上げられない
- 全か無かではなく重み付け。鍋でも刺激・香りを多少は足せる（最初から少しスパイシーな鍋、
  など）し、その逆も少しは可能

この2レイヤー構造は、コアビジョンの「会話しながら調理する"ながら作業"の没入感」と噛み
合う。鍋という共通の土台を育てつつ、会話しながら客ごとに最後のひと振り（刺激・香り）で
好みに寄せる、という体験。会話と調理が別レイヤーで並走できる。

## 統合演算とスケール設計（2026-08-16 追記。実装の基準）

> 前回メモで「操作手段の集約」までしか決めていなかった rich/light→コク統合の具体と、
> 味スケールの解像度（前回「未決の論点」だった項目）を確定した。

### rich/light → コクへの統合

- コクは単極1軸。値が高いほど濃厚（旧rich方向）、低いほどさらり（旧light方向）。旧 `rich` と
  `light` の「2フィールド」を、コク「1フィールド」に統合する。これにより「濃厚かつあっさり」
  という矛盾値が構造的に作れなくなる（軸設計欠陥の解消）
- 「lightフィールドを無くす」は「あっさりを表現できなくする」という意味ではない。あっさりは
  「コク軸の低い値」で表現される。あっさり系スープは低コク＋相応の旨味等で表す（前回確定の
  単極モデル通り）
- **移行方法**: 既存データ（ベース/トッピング/薬味/客ideal）の rich/light のペアを見て、各
  データが「濃厚寄りかさらり寄りか」を人が判断し、コク1軸の値を手で決め直す。機械的変換式
  （`rich - light` 等）は採らない（精進が0に潰れる・酢の負値 `rich=-1` で破綻する等の問題が
  あるため）
- 例（スケール0〜50、暫定）: 豚骨（旧rich5/light0）→コク高（濃厚）、精進（旧rich0/light5）→
  コク低（さらり）、クズ（旧rich1/light1）→コク低（薄い）。具体値は数値調整フェーズで確定

### 味スケールの解像度（前回「未決の論点」を確定）

- 全4軸（コク/旨味/刺激/香り）を共通スケールにする。各軸は単極の整数、0=その味が無い
  （お湯）、大きいほどその味が強い
- スケールの最大値の目安は50（0〜50）。旧来の0〜5程度の狭いレンジでは水1回・ベース1個の
  効果が相対的に大きすぎたのを、広いレンジで繊細に調整可能にする（例: 50=濃厚マックス、
  30=少し濃厚、25=普通、10=あっさり風味、1=あっさり）
- 最大値は変数（定数）で持つ。コード内に50を直書きせず、`TASTE_AXIS_MAX` 相当の定数1つを
  定義し、失敗判定の閾値・UIゲージ・その他「最大値基準で考える箇所」はそれを参照する。後で
  最大値を変えたくなったら1箇所の変更で済むようにする（調整が難しければ再検討する前提）
- ただし `SoupAttrs` のフィールド自体はint で、0〜50に強制はしない（intに上限制約コードは
  持たせない）。50はあくまで「データを作る際の目安」＋「割合計算の基準定数」。データ作成時の
  スケール感の目安として本ドキュメントにも明記しておく

### 仕組みと数値の切り分け（実装方針）

- **仕組み（実装する）**: `SoupAttrs` が4軸（コク/旨味/刺激/香り）のintを持つ。最大値目安の
  定数（`TASTE_AXIS_MAX=50`）。`Evaluator` が4軸で距離を測る。`Pot` の水/煮詰まりが4軸を
  動かす。評価2段構え（薄すぎ絶対失敗＋ideal距離）
- **数値（暫定で置き後調整）**: 各データの具体的な軸の値（豚骨のコクは何、客Aの理想コクは
  何）、操作の効き幅（水1回でコクが何下がるか）、失敗判定の具体閾値。これらは数値調整
  フェーズで詰める

### 刺激・香り（新設2軸）の初期値

刺激・香りは既存データに存在しないため、全ベース/トッピング/薬味/客idealに新規設定が必要
（変換ではなく創作）。刺激は薬味（生姜/にんにく/黒酢）が主担当、香りは香味系が主担当。具体値は
数値調整フェーズ。現状の食材で刺激・香りを十分動かせるかの棚卸しと、必要なら食材追加も実装
フェーズの前提作業。

### 次の一手（実装の入り口）

- 実装は `SoupAttrs` のフィールド入れ替え（rich/lightを消してコク追加、刺激・香りを追加）から。
  ただしこれは `SoupAttrs` を参照する全コード（evaluator/pot/game.gd/test系/各`.tres`）を
  同時に壊すため、安全な刻み方（一括変更か、軸を足してから引くか等）を実装着手時に設計する
- 移行対象データの棚卸しは現状把握済み（客ideal3・ベース3・トッピング3・薬味3、および
  セーブの `pot_carryover_*`）

### ステップ2（完了・コミット `0760590`）: rich/light→koku 統合

スコープを「rich/light の2軸を koku の1軸に畳む」ことに限定する（範囲A）。刺激・香りの評価
導入・評価2段構え（薄すぎ失敗判定）は含めない（ステップ3へ）。

**方針**:

- 刻み方は「一括」。中間状態（rich/light と koku の併存）は作らない。テストを安全網にして
  1コミットで統合する。理由: 「濃厚さ」を表す軸が旧richと新kokuで二重に存在する期間を作ると、

- **評価**: `distance_to()` は koku/umami の2軸のマンハッタン距離になる（旧 rich/light/umami
  の3軸から）。刺激・香りは器にあるが評価には入れない（`distance_to` に含めない、値も0のまま
  据え置き）
- **Pot**: 現状の rich 操作（煮詰まりで rich+1、水で rich-2/umami-1）を koku 操作に素直に
  読み替える。light は元々操作していないので統合で失うものはない。定数 `WATER_RICH`→
  `WATER_KOKU` 等をリネーム
- **Evaluator**: `_fill_worst_axis()` の diffs 辞書（現状 rich/light/umami の3軸ハードコード）
  を koku/umami の2軸に
- **game.gd / soup_serving / debug_pot**: UI表示・鍋再構築（`_build_zanryu_option` 等）の
  rich/light 参照を koku に
- **セーブ**: `GameState.pot_carryover_rich`/`pot_carryover_light` を `pot_carryover_koku` に
  畳む（umami はそのまま）。stimulus/aroma の持ち越しは今は足さない（ステップ3で評価に効くよう
  になってから）。旧セーブ互換: `pot_carryover_koku` は `.get(key,0)` デフォルトで読む。旧
  セーブ（rich/light形式）をロードすると鍋持ち越しは0になる（変換しない）。開発中のテスト
  セーブのみ持ち越しが失われるが、以降のセーブは koku 形式で正常に持ち越せる。実害なしと判断し
  許容。rich→koku の値変換を機械的にしない方針（下記データ）と一貫させ、セーブ値も機械変換
  しない
- **データ（.tres）**: 客ideal3・ベース3・トッピング3・薬味3 の koku 値を、既存の rich/light
  のペアを見て「濃厚寄りか、さらり寄りか」で手で決め直す。ただしステップ2では暫定値でよい
  （例: 豚骨=濃厚→koku高、精進=さらり→koku低、クズ=薄い→koku低。スケール50目安）。厳密な
  バランス調整は数値調整フェーズ（ステップ4）で。刺激・香りの値は0のまま据え置き

**作業順序（1コミット内）**: `SoupAttrs`（rich/light→koku、`distance_to` をkoku/umami計算に）
→ `Pot`（rich操作をkoku操作に、定数リネーム）→ `Evaluator`（diffs を koku/umami に）→
`game.gd`/`soup_serving`/`debug_pot`（参照を koku に）→ セーブ（`pot_carryover_koku` に畳む）→
`.tres`（koku値を暫定で振る）→ テスト（`test_evaluator`/`test_pot` を koku/umami ベースに
書き換え、実行して統合が正しいか検証）。

**検証**: 統合後、テストで「koku/umami の2軸評価が意図通り動くか（GREAT/OK/BAD判定、距離
計算）」を確認。ステップ2はスコープが koku統合に限定されるので、テストが通れば「統合が正しく
できた」ことが明確に切り分けられる。

### ステップ3（次回以降）: 刺激・香りの評価導入

前回メモでは「`distance_to` を4軸に単純拡張し、評価2段構え（薄すぎ絶対失敗＋ideal距離）を足す」
という素朴な案だった。今回、評価モデル自体を「合算距離としきい値」から「軸ごと合格判定」に
作り替える方針に見直した（下記サブステップ3-1）。以前のstimulus/aromaセーブ持ち越し・食材
棚卸しは、評価モデルが固まった後のサブステップ（3-2以降）に送る。

#### サブステップ3-1（次回実装）: 刺激・香りの評価導入（軸ごと合格判定モデル）

> 数値（Grade閾値・tolerance・客ideal・食材の刺激/香り値）はすべて暫定。ステップ4の数値
> バランス調整で確定させる前提の仮置き。

**スコープ**: 正の値による4軸評価の土台作りと `worst_axis` の4軸対応まで。引き算メカニクス・
黒酢の再設計・客ごとの軸重み・全軸0〜50スケール統一・クリティカル二段幅は含めない（次回以降）。

**評価モデルの転換**:

現行の「全軸の差を合算した単一距離（`distance_to`）を閾値と比較」する方式を廃し、「各軸ごとに
idealとの差がtolerance以内かを個別判定し、合格した軸の本数で段階を決める」方式に作り替える。
理由: 「何軸合ったか」による段階評価は合算距離では表現できない（1軸大外し＋他ピタリ、と全軸を
薄く外す、が同じ合計距離になり区別不能なため）。1軸ごとの合否という粒度に落とすことで、
「どこが合っていてどこが外れているか」を評価の構造そのものに埋め込む。

**軸ごと合格判定**: 各軸で `abs(cup値 - ideal値) <= tolerance[軸]` なら「その軸は合格」。

**合格本数→Grade**:

- 4軸合格 → GREAT（とても好み）
- 3軸合格 → GOOD（美味しい）
- 2軸合格 → OK（普通）
- 1軸合格 → OK（普通）
- 0軸合格 → BAD（イマイチ）

BADは全4軸が許容幅外＝ほぼ水か全軸大外しのときのみ。食品の性質上よっぽど失敗しない限り不満には
ならない、という設計方針の反映。

**Grade拡張**: 現行3値（GREAT/OK/BAD）を4値（GREAT/GOOD/OK/BAD）に拡張。payment/rep_delta への
波及あり。

**payment/rep_delta（暫定。基本あまり儲からない、自転車操業感を意図）**:

| Grade | payment | rep_delta |
|---|---|---|
| GREAT | base_price + tip | +1 |
| GOOD  | base_price       | +1 |
| OK    | base_price       | ±0 |
| BAD   | base_price × 0.5 | -1 |

GOOD と OK は支払い同額（満額）、評判のみ差を付ける。

**tolerance（軸ごとの定数、既存スケールを活かす。暫定）**:

- `TOLERANCE_KOKU = 8`
- `TOLERANCE_UMAMI = 2`
- `TOLERANCE_STIMULUS = 2`
- `TOLERANCE_AROMA = 2`

軸ごとにスケール感が違うため共通単一値ではなく軸別に持つ。全軸0〜50スケール統一はステップ4に
送るため、それまでは軸別toleranceで既存スケールを活かす（kokuだけ他軸よりレンジが広い現状に
合わせている）。

**great_threshold/ok_threshold（距離しきい値）の廃止**: 新モデルでは合格軸本数で判定するため
不要になる。`CustomerResource` からこの2フィールドを削除し、既存 `.tres` 3件（`keiji` の
`ok_threshold=4` 明示指定を含む）からも該当行を削除する。`distance_to()` 自体は評価では使わなく
なるが、デバッグ表示等での残置可否は実装時に判断する。

**worst_axis**: `_fill_worst_axis()` の `diffs` 辞書を `koku`/`umami`/`stimulus`/`aroma` の
4キーに拡張する。台詞接続（設計書9章）は未実装のままでよく、今回は4軸でworst判定が回るところ
まで。

**客idealの設計方針（キャラ性に基づく。数値は暫定・後日調整）**:

- 老人（`roujin`）: あっさり・旨味高・香り高・スパイス苦手 → koku=10, umami=4, stimulus=0,
  aroma=4
- 配達員（`haitatsuin`）: こってり・旨味普通・香り普通・スパイス好き → koku=45, umami=4,
  stimulus=4, aroma=2
- 刑事・元料理人（`keiji`）: こってり・香り良い・旨味普通・スパイス普通 → koku=25, umami=5,
  stimulus=2, aroma=4

注記: 「スパイス苦手」は `ideal.stimulus=0` で表現する。今回のモデルは「苦手」と「無関心」を
区別しないため、刺激を入れると老人はその軸を1本落とすだけになる（BADにはならない。刺激込みで
も他3軸が合格すればGOOD止まりで着地する）。

**食材のstimulus/aroma設計方針（薬味=刺激/香り主担当、香味系が香り、ベース/トッピングは控えめ。
数値は暫定）**:

- 生姜（`yak_shoga`）: stimulus=2, aroma=4（koku=0, umami=1 維持）

#### サブステップ3-2（次回実装）: 客ごとの軸別tolerance上書き（案B・手動明示）

> 数値（tolerance値・狭め/広めの目安）はすべて暫定。ステップ4の数値バランス調整で確定させる
> 前提の仮置き。

**目的**: 「刺激さえ合えば他の軸は雑でも満足する」のような客ごとの関心差を表現する。現状の全客
共通tolerance（`soup_attrs.gd`の定数）を、客ごとに軸別で上書きできるようにする。関心の薄い軸は
toleranceを広げることで「多少ぶれても合格」＝寛容さとして表現し、こだわる軸は狭めることで
「ぴったりでないと不満」を表現する。

**スコープ**: 評価の骨格（4軸で合格判定→合格軸数でGrade決定、4→GREAT/3→GOOD/2,1→OK/0→BAD）は
一切変更しない。変わるのは各軸の合格幅の出どころが「全客共通定数」から「客ごとの上書き値 or
共通定数のフォールバック」になる点のみ。Gradeマッピング・payment/rep_delta・worst_axisロジック
は無変更。引き算食材（黒酢）・全軸0〜50スケール統一・軸の重み付きスコア化（案C）は含めない。

**設計方針（案の比較を記録）**: 客ごとの個性表現には案A（関心軸だけで判定、分母可変）・案B
（軸別tolerance上書き、常に4軸判定）・案C（重み付きスコア化）を検討した。案Cはステップ3-1で
合算距離を捨てて段階モデルにした思想と衝突するため見送り。案Aは分母が客ごとに変わりGrade
マッピングを合格率ベースに作り替える必要があるため見送り。案Bは段階モデルを壊さず、tolerance
差だけで「うるさい客＝狭い/無関心な客＝広い」を連続的に表現できるため採用。「刺激さえ合えば
他軸は雑でも満足する」という要望は「他軸のtoleranceが広い客」として案Bで表現できる。

**tolerance生成方式**: content-driven（客ごとに軸別toleranceを明示的に振る、アルゴリズム自動
生成はしない）。「重視軸を1つ決めて他を自動で広げる」ロジックは、組み合わせの妙や中間的な好み
（配達員は刺激重視だが旨味もそこそこ等）を潰すため採用しない。同席パターンを明示列挙にした
判断（3-1以前の設計）と同じ方針。

**実装方式（番兵フォールバック）**: `CustomerResource`に軸別toleranceフィールドを追加する
（`tolerance_koku`/`tolerance_umami`/`tolerance_stimulus`/`tolerance_aroma`）。デフォルト値は
「未指定」を意味する番兵 `-1`。評価時、客の該当軸の値が `-1` なら `soup_attrs.gd` の共通定数
（`TOLERANCE_KOKU`等）をフォールバックで使い、0以上なら客の上書き値を使う。これにより客は
上書きしたい軸だけ`.tres`に書けばよく、既存のフォールバック思想（`.get(key, default)`）とも
整合する。共通定数は「デフォルトの基準値」として残す。

**evaluate()の変更点**: 各軸の合格判定で、tolerance参照を「`SoupAttrs.TOLERANCE_xxx` 固定」
から「客の`tolerance_xxx`が`-1`なら共通定数、そうでなければ客の値」を返すヘルパー経由に変える。
判定式・合格カウント・Grade決定は無変更。

**客3人のtolerance設計方針（キャラ性に基づく、数値は暫定・後日調整。`-1`は共通定数フォール
バック＝標準の寛容さ）**:

- 老人（`roujin`、あっさり・旨味と香りにこだわる・スパイス苦手）: umami狭め（こだわる）,
  aroma狭め（こだわる）, koku標準, stimulus広め（ideal=0から多少ぶれても気にしない）
- 配達員（`haitatsuin`、こってり・刺激好き・旨味と香りは雑でOK）: stimulus標準〜やや狭め
  （刺激は合ってほしい）, umami広め（雑でOK）, aroma広め（雑でOK）, koku標準
- 刑事（`keiji`、こってり・香り良いものを好む・旨味と刺激は普通）: aroma狭め（香りにこだわる）,
  umami標準, stimulus広め（こだわらない）, koku標準

具体値は実装時に詰める。狭め/広めの目安（暫定）: 狭め=1, 標準=共通定数（`-1`で継承）, 広め=
共通定数の2倍程度。

**実装の触るファイル（次セッションで詰める。この文書では列挙まで）**:

- `resources/customer_resource.gd`: `tolerance_koku`/`tolerance_umami`/`tolerance_stimulus`/
  `tolerance_aroma` フィールド追加、デフォルト`-1`
- `core/evaluator.gd`: tolerance参照を客上書き対応のヘルパー経由に。合格判定ロジック自体は
  無変更
- 客ideal 3件の`.tres`: 上書きしたい軸のtolerance値を追加、共通のままにする軸は書かない
- `core/test_evaluator.gd`: 客別toleranceで合格幅が変わるケースを追加。フォールバック（`-1`で
  共通定数を使う）ケースと、上書きで幅が変わるケースの両方を検証
- `soup_attrs.gd`の共通定数は変更なし（基準値として残す）

**注記**: 老人の「スパイス苦手」は依然`ideal.stimulus=0`で表現し、`tolerance_stimulus`を
広げることで「刺激をある程度入れても即失点はしないが、ideal=0基準なので入れすぎれば落ちる」
という寛容さを表す。「苦手（入れると嫌がる）」と「無関心」の厳密な区別、および引き算食材
（黒酢で刺激を下げる）は引き続き別サブステップ。

#### サブステップ3-3（次回実装）: 引き算食材メカニクス（黒酢の刺激↓・コク↓）

> 数値（黒酢の koku/stimulus 値含む）はすべて暫定。ステップ4の数値バランス調整で確定させる
> 前提の仮置き。

**目的**: 「コクを下げ、刺激も下げる引き算調味料」としての黒酢を機能させる。ステップ3-1で
黒酢は `stimulus=0, aroma=0`（koku含め実質全軸0）に一時停止し、「引き算メカニクスの再設計は
次回」と据え置いていた。その宿題を返す。食材が負の `attrs` を持てるようにし、投入で軸が下がり、
0で下げ止まる（下限クランプ）仕組みを入れる。

**スコープ**: 負値食材の投入と下限0クランプの導入まで。評価モデル（軸ごと合格判定→合格軸数で
Grade）・客ごとのtolerance（サブステップ3-2）・Grade値・payment/rep_deltaには一切触れない。
上限クランプ（`TASTE_AXIS_MAX=50` での頭打ち）は今回入れない（現状intに上限強制していない
方針を維持、ステップ4で検討）。全軸0〜50スケール統一もステップ4。

**背景（現状の非対称性）**: 現状 `add()` は無条件加算でクランプなし。下限0クランプは
`Pot.add_water()` の koku/umami にだけ手書きで存在する（stimulus/aromaにはクランプも水補正も
ない）。この非対称を、`SoupAttrs` に下限0クランプを一本化することで解消する。

**クランプ方式（案ウを採用）**: `SoupAttrs` に全4軸を下限0に丸めるメソッド（例:
`clamp_to_zero() -> void`、各軸を `maxi(軸, 0)` する）を新設する。`add()` は純粋加算のまま
変更しない。投入処理が加算を全部終えた後にこのメソッドを1回呼ぶ。

- 案ア（`add()` 内にクランプ内蔵）: `add()` の純粋性を失うため不採用
- 案イ（Pot内で軸ごとに手書き `maxi`）: クランプロジックが散るため不採用
- 案ウ（採用）: クランプロジックが `SoupAttrs` に1箇所集約され、呼ぶ場所が明示され、
  `Pot.add_water()` の既存手書き `maxi` もこのメソッドに一本化できる。「状態の明確性優先」
  原則に沿う

**クランプ対象**: 全4軸（koku/umami/stimulus/aroma）。今引く食材があるのはkoku/stimulusだが、
将来どの軸に引き算食材が来ても守られるよう全軸を対象にする。

**クランプのタイミング（最後に1回）**: 投入の最後に1回だけclampを呼ぶ。順序依存を避けるため、
各 `add()` ごとには丸めない。

- `Pot.serve()`: topping・yakumiを全て `add()` し終えた後、`cup.attrs` にclampを1回
- `Pot.setup()`: baseにpot_ingredientsを全て `add()` し終えた後、`attrs` にclampを1回（現状
  `pot_ingredients` は空だが、将来の鍋への追加投入UIに備えて一貫させる）
- `Pot.add_water()`: 既存のkoku/umami手書き `maxi` を廃し、水補正を全て足した後にclampを1回
  呼ぶ形に統一（stimulus/aromaは水補正しないが、clamp自体は全軸に掛かる）

理由: 「加算のたびにクランプ」だと同時投入で投入順（topping→yakumi固定）に最終値が依存する
（例: 黒酢とにんにくを同時投入時、先に黒酢で0クランプしてからにんにくを足すか、先ににんにくを
足してから黒酢を引くかで結果が変わる）。順序依存を避け「一杯の最終状態を0で守る」意味を明確に
するため、最後に1回クランプとする。

**黒酢の値（暫定、ステップ4調整前提）**: `yak_kurozu.tres` を `koku=-4, stimulus=-4, umami=0,
aroma=0` に設定。コクと刺激を下げる引き算調味料として機能させる。数値のバランス（既存食材は
koku最大40・stimulus最大4程度）はステップ4で調整。

**実装の触るファイル（次セッションで詰める。この文書では列挙まで）**:

- `core/soup_attrs.gd`: `clamp_to_zero()` メソッド新設
- `core/pot.gd`: serve/setupの投入後にclamp呼び出し追加、add_waterの手書き `maxi` をclampに
  一本化
- `data/recipes/yakumi/yak_kurozu.tres`: `koku=-4`/`stimulus=-4` に設定
- `core/test_pot.gd`: 黒酢投入でkoku/stimulusが下がり0で下げ止まることを検証、引きすぎても
  負にならないこと、水差しのクランプ一本化後も既存挙動が保たれることを検証

**注記**: 黒酢が刺激を下げられるようになったことで、「刺激を嫌う客（老人、`ideal.stimulus=0`）
に対し、誤って刺激を入れてしまったスープを黒酢で救う」といったプレイングが理屈上可能になる。
ただし今回は仕組みの導入までで、そうした救済が実際に成立するかのバランス確認・演出はステップ4
および実プレイで詰める。
