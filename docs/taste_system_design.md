## 背景・動機

現状の味ステータスは `rich`（濃厚）/ `light`（あっさり）/ `umami`（旨味）の3軸（int）。

**問題**: `rich` と `light` は相反する概念なのに独立した2軸になっているため、「rich高かつ
light高」という味としてイメージできない矛盾状態が数値上は作れてしまう。軸設計の欠陥。

**方針**: 相反する概念は1軸の両端に統合し、矛盾を構造的に排除する。あわせて味の表現力を
上げるため軸を再構成する。

## 新しい4軸の定義

各軸は「1本のスライダー、両端に対義の味」。内部表現は単極（後述）。

| 軸 | 両端 | 内容 |
|---|---|---|
| コク | 濃厚 ⇔ さらり | 質感・口当たりの重さ。現 `rich`/`light` を1軸に統合 |
| 旨味 | 深み ⇔ 平坦 | 出汁の効き。現 `umami` を踏襲 |
| 刺激 | パンチ ⇔ マイルド | 塩気・辛み・スパイス。新設 |
| 香り | 芳醇 ⇔ 淡泊 | 香味野菜・ハーブの効き。新設 |

- 例: 濃い味スープ = 「コク:濃厚 旨味:深み 刺激:パンチ 香り:芳醇」
- 例: お湯に近い失敗作／病院食 = 「全軸が低い」

## 内部表現: 単極（案X）を採用

各軸は0以上の値。0=下端（さらり/平坦/マイルド/淡泊＝その味が無い）、値が大きいほど上端
（濃厚/深み/パンチ/芳醇）。お湯＝全軸ほぼ0。

- 双極（0=中央、負=さらり方向）は採用しない。理由: 表現したい「お湯=何も無い状態」は
  「全軸0」で素直に表せる。双極だとお湯が中央値になり直感に合わない
- 単極でも「さっぱり系の完成した味」は表現できる。評価は「値の高低」ではなく「客の
  `ideal` との距離」で決まるため、薄味好きの客は `ideal` が低い座標を指し、薄いスープ
  ほど距離が近く高評価になる（下記「評価の構造」参照）
- ※現状の型は int。レンジを大きく取って繊細な調整を可能にする案は別途「味スケールの
  解像度」課題として扱う（float化は採らない）

## 評価の構造: 2段構え

### 第1段（失敗判定・絶対ルール）

- 複数の軸が「薄すぎる」（お湯に近い）スープは、客の好みに関わらず低評価。「料理として
  成立していない」ことを表す
- 具体的な閾値（何軸未満を薄いとみなすか）と軸数（何軸以上が薄いと失敗か。相談では
  「3種以上」案が出た）は数値バランスであり、実装フェーズで要調整。仕組みとして存在
  することだけを今は確定する

### 第2段（好み評価）

- 第1段を通過した「成立しているスープ」を、客ごとの `ideal` との距離で評価。既存
  `Evaluator` の `distance_to`（attrs距離）を4軸に拡張して踏襲する
- 「濃すぎ」は絶対ルールに含めない。濃すぎるスープはそれを `ideal` とする客がいなければ
  全客の `ideal` から遠く、第2段の距離評価で自然に低評価になるため。上限を絶対ルールで
  縛る必要はなく、客の好み（`ideal`）調整で対応できる。薄すぎ（お湯）のみ非対称に絶対
  ルールで蓋をする

## 各軸を動かす手段（操作の割り当て）

軸を定義しても、それを動かす手段がなければ軸は機能しない。各軸の主担当を割り当てる。

- **コク**: ベースの濃さ ＋ 水を足す（下げる）／ベースを足す（上げる、将来仕様の
  `add_base` 相当）＋ 煮詰まり（煮込むと上がる）。操作手段が最も豊富。既存 `rich`/`light`
  の動きがここに集約される
- **旨味**: ベースの質 ＋ 鍋に入れる具材 ＋ 煮詰まり（煮込むほど出汁が出る）
- **刺激**: 薬味が主担当（辛み・塩気）。新設軸のため既存の薬味を刺激軸に紐付ける設計が
  必要
- **香り**: 香味野菜・ハーブ系が主担当。新設軸のため、香りを上げる食材の割り当て、また
  は新カテゴリ追加が必要になりうる

※刺激・香りは新設軸なので、それらを動かす食材が現状（トッピング3・薬味3）で足りるかの
棚卸しと、必要なら食材追加が実装フェーズの前提作業になる。

## 鍋レイヤーとカップレイヤーの非対称構造

味を作る場を2レイヤーに分け、各軸が動きやすいレイヤーを非対称に重み付けする。この非対称
は料理の物理から導かれる（ゲームルールではなく必然）。

- **鍋レイヤー**（量が多い・全客共通・営業前〜営業中にじわじわ育つ）: コク・旨味が大きく
  動く（煮込みで作る味）。刺激・香りは鍋に足しても量に薄まって効果が小さい
- **カップレイヤー**（一杯分・量が少ない・客ごとにサーブ時調整）: 刺激・香りが大きく
  動く（タバスコ、パクチー山盛りのように少量で効く）。コク・旨味は「煮ないと出ない」ため
  サーブ時には大きく上げられない
- 全か無かではなく重み付け。鍋でも刺激・香りを多少は足せる（最初から少しスパイシーな鍋、
  など）し、その逆も少しは可能

この2レイヤー構造は、コアビジョンの「会話しながら調理する"ながら作業"の没入感」と噛み
合う。鍋という共通の土台を育てつつ、会話しながら客ごとに最後のひと振り（刺激・香り）で
好みに寄せる、という体験。会話と調理が別レイヤーで並走できる。

## 未決の論点（実装フェーズで判断）

- **同じ具材・薬味を複数個入れられるようにするか**（「パクチー山盛り」表現）:
  - 案1（1個ずつ・量なし）: 各薬味は入れる/入れないの2値。シンプル。既存UIの延長
  - 案2（複数個・量あり）: 同じ薬味を複数入れられ量が効果に比例。表現力は高いが個数調整
    UIが要り、操作が一手増える。会話への集中を削ぐリスク
  - 方針（暫定）: 当面は案1で仕組みを作り、案2は拡張余地として残す。将来の
    `add_water(times)` / `add_base` と同じ「times構造」で案1→案2は後から拡張可能なため、
    最初から複雑さを抱えない。ただし「山盛りでゲロマズにして特定客が喜ぶ」等が体験の核に
    なるなら案2を早めに入れる判断もありうる。体験の狙いと相談して実装フェーズで決める

- 刺激・香りを動かす食材の具体的な割り当て・追加

## 統合演算とスケール設計（2026-08-16 追記。実装の基準）

> 前回メモで「操作手段の集約」までしか決めていなかった rich/light→コク統合の具体と、
> 味スケールの解像度（前回「未決の論点」だった項目）を確定した。

### rich/light → コクへの統合

- コクは単極1軸。値が高いほど濃厚（旧rich方向）、低いほどさらり（旧light方向）。旧 `rich` と
  `light` の「2フィールド」を、コク「1フィールド」に統合する。これにより「濃厚かつあっさり」
  という矛盾値が構造的に作れなくなる（軸設計欠陥の解消）
- 「lightフィールドを無くす」は「あっさりを表現できなくする」という意味ではない。あっさりは
  「コク軸の低い値」で表現される。あっさり系スープは低コク＋相応の旨味等で表す（前回確定の
  単極モデル通り）
- **移行方法**: 既存データ（ベース/トッピング/薬味/客ideal）の rich/light のペアを見て、各
  データが「濃厚寄りかさらり寄りか」を人が判断し、コク1軸の値を手で決め直す。機械的変換式
  （`rich - light` 等）は採らない（精進が0に潰れる・酢の負値 `rich=-1` で破綻する等の問題が
  あるため）
- 例（スケール0〜50、暫定）: 豚骨（旧rich5/light0）→コク高（濃厚）、精進（旧rich0/light5）→
  コク低（さらり）、クズ（旧rich1/light1）→コク低（薄い）。具体値は数値調整フェーズで確定

### 味スケールの解像度（前回「未決の論点」を確定）

- 全4軸（コク/旨味/刺激/香り）を共通スケールにする。各軸は単極の整数、0=その味が無い
  （お湯）、大きいほどその味が強い
- スケールの最大値の目安は50（0〜50）。旧来の0〜5程度の狭いレンジでは水1回・ベース1個の
  効果が相対的に大きすぎたのを、広いレンジで繊細に調整可能にする（例: 50=濃厚マックス、
  30=少し濃厚、25=普通、10=あっさり風味、1=あっさり）
- 最大値は変数（定数）で持つ。コード内に50を直書きせず、`TASTE_AXIS_MAX` 相当の定数1つを
  定義し、失敗判定の閾値・UIゲージ・その他「最大値基準で考える箇所」はそれを参照する。後で
  最大値を変えたくなったら1箇所の変更で済むようにする（調整が難しければ再検討する前提）
- ただし `SoupAttrs` のフィールド自体はint で、0〜50に強制はしない（intに上限制約コードは
  持たせない）。50はあくまで「データを作る際の目安」＋「割合計算の基準定数」。データ作成時の
  スケール感の目安として本ドキュメントにも明記しておく

### 仕組みと数値の切り分け（実装方針）

- **仕組み（実装する）**: `SoupAttrs` が4軸（コク/旨味/刺激/香り）のintを持つ。最大値目安の
  定数（`TASTE_AXIS_MAX=50`）。`Evaluator` が4軸で距離を測る。`Pot` の水/煮詰まりが4軸を
  動かす。評価2段構え（薄すぎ絶対失敗＋ideal距離）
- **数値（暫定で置き後調整）**: 各データの具体的な軸の値（豚骨のコクは何、客Aの理想コクは
  何）、操作の効き幅（水1回でコクが何下がるか）、失敗判定の具体閾値。これらは数値調整
  フェーズで詰める

### 刺激・香り（新設2軸）の初期値

刺激・香りは既存データに存在しないため、全ベース/トッピング/薬味/客idealに新規設定が必要
（変換ではなく創作）。刺激は薬味（生姜/にんにく/黒酢）が主担当、香りは香味系が主担当。具体値は
数値調整フェーズ。現状の食材で刺激・香りを十分動かせるかの棚卸しと、必要なら食材追加も実装
フェーズの前提作業。

### 次の一手（実装の入り口）

- 実装は `SoupAttrs` のフィールド入れ替え（rich/lightを消してコク追加、刺激・香りを追加）から。
  ただしこれは `SoupAttrs` を参照する全コード（evaluator/pot/game.gd/test系/各`.tres`）を
  同時に壊すため、安全な刻み方（一括変更か、軸を足してから引くか等）を実装着手時に設計する
- 移行対象データの棚卸しは現状把握済み（客ideal3・ベース3・トッピング3・薬味3、および
  セーブの `pot_carryover_*`）

## 実装ステップと進め方（2026-08-17 追記）

味システム4軸化を段階に分けて実装する。各ステップの検証を明確にするためスコープを絞る。

### ステップ1（完了・コミット `e11611e`）

`SoupAttrs` に刺激 `stimulus`・香り `aroma` の2軸と `TASTE_AXIS_MAX=50` 定数を追加。既存
`rich`/`light`/`umami` は残し、`add()`/`duplicate_attrs()` に新軸を反映、`distance_to()` は
据え置き（評価挙動不変）。既存テストPASS・`.tres` 互換を確認済み。器を安全に広げた過渡段階
（5フィールド）。

### ステップ2（次回実装）: rich/light→koku 統合

スコープを「rich/light の2軸を koku の1軸に畳む」ことに限定する（範囲A）。刺激・香りの評価
導入・評価2段構え（薄すぎ失敗判定）は含めない（ステップ3へ）。

**方針**:

- 刻み方は「一括」。中間状態（rich/light と koku の併存）は作らない。テストを安全網にして
  1コミットで統合する。理由: 「濃厚さ」を表す軸が旧richと新kokuで二重に存在する期間を作ると、
  どちらが正か曖昧になり判断しづらい。状態を常に明確に保つため一括で畳む
- **評価**: `distance_to()` は koku/umami の2軸のマンハッタン距離になる（旧 rich/light/umami
  の3軸から）。刺激・香りは器にあるが評価には入れない（`distance_to` に含めない、値も0のまま
  据え置き）
- **Pot**: 現状の rich 操作（煮詰まりで rich+1、水で rich-2/umami-1）を koku 操作に素直に
  読み替える。light は元々操作していないので統合で失うものはない。定数 `WATER_RICH`→
  `WATER_KOKU` 等をリネーム
- **Evaluator**: `_fill_worst_axis()` の diffs 辞書（現状 rich/light/umami の3軸ハードコード）
  を koku/umami の2軸に
- **game.gd / soup_serving / debug_pot**: UI表示・鍋再構築（`_build_zanryu_option` 等）の
  rich/light 参照を koku に
- **セーブ**: `GameState.pot_carryover_rich`/`pot_carryover_light` を `pot_carryover_koku` に
  畳む（umami はそのまま）。stimulus/aroma の持ち越しは今は足さない（ステップ3で評価に効くよう
  になってから）。旧セーブ互換: `pot_carryover_koku` は `.get(key,0)` デフォルトで読む。旧
  セーブ（rich/light形式）をロードすると鍋持ち越しは0になる（変換しない）。開発中のテスト
  セーブのみ持ち越しが失われるが、以降のセーブは koku 形式で正常に持ち越せる。実害なしと判断し
  許容。rich→koku の値変換を機械的にしない方針（下記データ）と一貫させ、セーブ値も機械変換
  しない
- **データ（.tres）**: 客ideal3・ベース3・トッピング3・薬味3 の koku 値を、既存の rich/light
  のペアを見て「濃厚寄りか、さらり寄りか」で手で決め直す。ただしステップ2では暫定値でよい
  （例: 豚骨=濃厚→koku高、精進=さらり→koku低、クズ=薄い→koku低。スケール50目安）。厳密な
  バランス調整は数値調整フェーズ（ステップ4）で。刺激・香りの値は0のまま据え置き

**作業順序（1コミット内）**: `SoupAttrs`（rich/light→koku、`distance_to` をkoku/umami計算に）
→ `Pot`（rich操作をkoku操作に、定数リネーム）→ `Evaluator`（diffs を koku/umami に）→
`game.gd`/`soup_serving`/`debug_pot`（参照を koku に）→ セーブ（`pot_carryover_koku` に畳む）→
`.tres`（koku値を暫定で振る）→ テスト（`test_evaluator`/`test_pot` を koku/umami ベースに
書き換え、実行して統合が正しいか検証）。

**検証**: 統合後、テストで「koku/umami の2軸評価が意図通り動くか（GREAT/OK/BAD判定、距離
計算）」を確認。ステップ2はスコープが koku統合に限定されるので、テストが通れば「統合が正しく
できた」ことが明確に切り分けられる。
