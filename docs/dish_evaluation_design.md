## なぜ転換するか

元案『夜湯』の核は「会話から客の事情を察し、限られた材料でどう応えるか」という人間ドラマと
資源配分にある。元案は明示的に次を述べていた。「正解レシピを当てるゲームではない」「最高評価
の料理が必ずしも物語上の最善ではない」。

しかし実装は、6軸（koku/umami/stimulus/aroma/sweet/sour）×二層評価（レシピ軸＋好み軸）×
5値Grade×メニュー再現、という「味を精密に採点し、正解レシピへの一致度を測る」方向に育った。
これは技術的には正しく動くが（5-3まで実装・検証済み）、元案の重心（事情への適合）から乖離し、
Coffee Talk型（注文された料理を再現する）に寄っていた。

実際に6軸を作って動かしたことで、この機構が「事情に応えるゲーム」には過剰であり、コンセプト
とズレていると判明した。動かしてみたからこそ過剰と分かった、という意味で6軸の実装は方向を
見極めるために必要な回り道だった。本転換はサンクコストに引きずられず、コンセプトに必要な
ものだけを残す判断である。

## 新しい評価設計の骨子

### 3層評価（核心）

評価を3層に分離する。

1. 料理として成立しているか（客と無関係な最低品質）
2. 味の組み合わせがよいか（食材の相性）
3. その客が今夜求めているか（事情への適合）

核心は「料理として美味い」と「その客が喜ぶ」を別判定にすること。これにより「美味しいが客には
合わない」「少し変な味だが客の事情には合っている」が両立する。元案の「最高評価の料理が物語上
の最善とは限らない」を、評価構造そのものに埋め込む。例: 濃厚な豚肉と鶏足のスープは料理として
は美味いが、胃弱の客には「旨いが今日はきつい」。薄い具沢山スープは味は凡庸だが、空腹で金の
ない客には最適で深く感謝される。

### 具材か料理か → 具材にタグと味を持たせる

具材（具材・調味料・香辛料）それぞれに、味パラメータと性質タグを持たせる。料理（組み合わせ）
単位ではタグを持たせない。一杯の味・効能は、入れた具材のタグと味の集合で決まる。

料理（組み合わせ）は正解として固定しない。タグ相性ルール（良い相性・悪い相性を少数）で緩く
評価する。これにより、正解の料理を作らなくても事情に応えられ（事情適合・品名を問わない）、
かつでたらめな組み合わせは相性ルールで美味しそう感が下がる（料理の説得力）。事情適合の自由さ
と料理の説得力を両立する。

「レシピ通り以外は失敗」は採らない。それではオリジナル料理が原則失敗になり、自由調理が形だけ
になるため。

### 客＝事情＋嗜好

客は「今夜の事情」（当日の状態＝冷えている・腹が減っている・気が沈んでいる・怪我を隠している
等）と「固定嗜好」（辛いのが好き・あっさり好み等）を持つ。事情がどの効能・味の方向を求めるかを
決め、嗜好は常に効く好みの方向。評価3層目（事情適合）は、一杯のタグ・味集合がこの事情/嗜好の
求めるものに噛み合うかを見る。

### オリジナル料理とレシピ帳（育つ記録）

- レシピ帳はプレイヤーが参照できる（手がかりを持たせる。全くの手探りにはしない）。
- レシピ帳の性格は「正解の品書き」ではなく、効能・意味・来歴の記録。事情への手がかりとして
  機能し、物語フラグで記述が育つ（例: 最初は「病人向けの一杯」だったものが、後に「老人の
  好物」だと分かる）。
- 完成度が一定以上のオリジナル料理は「名もなき一杯」として料理帳に登録する。客が高く評価すれ
  ば、その客が名前を付ける（例: 配達人が命名した「夜明け前の腹ごしらえ」）。正規レシピは「安全
  に一定品質を出す方法」、オリジナルは「リスクを取って客に深く応える方法」と位置づける。

### 評価表示は数値でなく言葉

プレイヤーに「相性+3」「完成度72」と見せると最適化パズルに見える。店主の試食コメントと客の
台詞でフィードバックする（例: 店主「苦味は強いが、豚の脂が受け止めている」、客「腹は満ちた。
それで十分だ」）。失敗理由をプレイヤーが台詞から推測できるようにする。

## 実装方針: 浅い版から

初回実装は浅い版から始める。味パラメータのフル多軸化や100点満点の重み付きスコア計算は今は
採らない。事情適合・料理成立（ざっくり）・オリジナル登録が動く最小形から着手し、味パラメータ
や相性ルールの細かさは実際に遊んでから足す（仕組みと数値の分離、まず動くものを作る）。深い版
（味8軸フル、100点スコア、料理評価と客評価の二重スコア）に最初から入ると、6軸二層を捨てて似た
複雑さに戻ることになり、今回の転換の意味を失う。

浅い版の最小形の定義（どの味パラメータを持つか、性質タグと相性ルールをどこまで、事情をどう
表現するか、評価をどう台詞に落とすか）は、次の設計フェーズで詰める。

## 既存6軸実装の扱い

6軸味システム（SoupAttrs 6軸・二層評価・5値Grade・taste_offset・tolerance・MenuResource）は
思想としては退場する。ただし処理パイプラインの骨格（Pot に具材を入れて SoupServing を作り、
Evaluator で客と照合して Result を返す）は、中身を「数値軸→タグ＋味パラメータ」「距離計算→
タグ相性＋事情適合」に入れ替えることで再利用しうる。器は生き、中身の思想は入れ替わる。捨てる
／活かすの具体的な仕分けは、浅い版の実装設計時に判断する。

## スコープ外・今後の論点

- 味パラメータの多軸化・重み付きスコア（深い版）は、浅い版で手応えを見てから必要に応じて。
- 昼の探索・経営の複雑さは増やさない（元案の自己抑制「昼を複雑にしすぎると会話ゲームの魅力が
  薄まる」を維持）。
- 具材の見た目自動変換（豚肉→豚軟骨/ひき肉/つみれ）、季節・曜日限定具材、茶碗蒸し等の完成品
  扱いは、料理コンテンツ設計フェーズで。

## 追補（2026-08-25）: 経済出力と鍋の資源管理

> 状態: 設計確定。実装は未着手。数値はすべて暫定で、実プレイで調整する。
>
> 本文（3層評価）は「一杯をどう評価するか」を定めるが、そこから金銭がどう出るか、
> 鍋という有限資源をどう扱うかは未定義だった。本追補でその2点を確定する。
> 参照した仕様書 Night Broth Cooking Evaluation System Design v0.3 の未定義箇所への回答。

### 1. 経済出力: 3つの出口を分離する

3層評価を単一の総合点に畳まないという原則を、経済にも適用する。支払・評判・会話を
それぞれ別の層に紐づけ、一つの最適化目標を作らない。

| 層 | 出口 | 理由 |
|---|---|---|
| 料理成立 | 支払（金） | 屋台の客は「食えるものが出たから払う」 |
| 事情適合 | 評判（→翌日以降のモブ客数） | 事情を察することを金に直結させない |
| 固定嗜好・物語フラグ | 会話・分岐・料理帳 | 数値化しない（本文9章の方針を維持） |

事情への応答は金銭ではなく、街での評判を経由して間接的に経済へ効く。「あの屋台は
分かってる」という評判がモブ客を呼ぶ。これにより、事情当てが金策にならない。

#### 1.1 支払

- 基本は客ごとの定価（屋台のスープなので客間の差は小さい）。
- 料理成立で決まる。VALID/FLAWED は定価、FAIL は減額。
- **FAIL時の扱いはキャラクター別**。貧しい客（老婆等）には無銭もありうる。
  経済ルールが同時にキャラクター描写になる。
- **チップは実装しない**。この街に裕福な客はいない、という世界観による。
  イベントでの例外的扱いのみ余地を残す。

#### 1.2 キャラクター別の減額と、その定着のさせ方

老婆は普段から半額とする。ただしこれをシステムの既定値として最初から与えるのではなく、
**初日にイベントとして「半分をおつりとして返すか」をプレイヤーに選択させ、以後その選択が
習慣として自動適用される**形にする。

意図: 半額は「システムがそう決めた」のではなく「あの夜プレイヤーがそうした」から続く。
店主の人となりをプレイヤーが選び、それが日常として定着する。数字が関係の記録になる。
以後は自動適用で作業化を避け、事情が特に厳しい夜など特定の場面でのみ再び選択を立ち上げる。

#### 1.3 評判とモブ客

- 常連6人だけでは低単価×少人数で経営が回らない。**常連は物語、モブは経済**と役割を分ける。
- 事情適合（MATCH/PARTIAL/MISS）が評判を動かし、評判が翌日以降のモブ客数を決める。
- **モブに調理は発生しない**。鍋からよそって出すだけ。プレイヤーが手を動かすのは常連の一杯のみ。
  会話ゲームとしての密度を守る（元案の「昼を複雑にしすぎると会話ゲームの魅力が薄まる」に対応）。
- **モブの挿入位置は常連と常連の幕間**。会話中に割り込まない。
  常連Aとの一連（会話→調理→提供→反応）が終わり、Bが来るまでの間に挟まる。
  幕間が「ただの間」ではなく資源が動く時間になり、屋台に人が出入りしている質感も出る。

### 2. 鍋: 有限で、変質し、水でしか戻せない

鍋を「一晩を通じて減り、変質していく共通資源」として設計する。元案の「限られた食材を
誰にどう配分するか」を、鍋の配分として実装する。

#### 2.1 量と濃度

- 鍋の総量は昼の仕込みで決まる有限量。一晩を通じて減る。
- 濃度は4段階: **薄い / 適正 / 濃い / 煮詰まり**。
- **開始段階は「適正」**。放置すれば濃くなる一方で、水を入れないと戻らない。
- **段階が進む契機はモブ客を捌いた後**。常連ひとりに一杯出した程度では変質しない。
  モブは複数人まとめて捌くため、時間が経ち、量が減り、その分煮詰まる。
  この処理で「売上・鍋量・濃度」が同時に動く。

#### 2.2 濃度段階が供給するタグ

鍋の状態は数値ではなくタグで表し、具材と同じ土俵に乗せる。既存の成立・相性・事情適合
ルールがそのまま適用でき、新しい判定ロジックを足す必要がない。

| 段階 | 供給タグ | 評価への影響 |
|---|---|---|
| 薄い | 淡泊・軽い | 旨味源としてカウントされない（V04に近づく）。胃が重い・疲労の客には合う |
| 適正 | 旨味 | 最も扱いやすい標準状態 |
| 濃い | 旨味・コク | コク強1つ分としてカウント（V05の片棒を担ぐ） |
| 煮詰まり | コク強・塩気 | 塩味源1つ分にもカウント（V01に近づく）。支える工夫が要る |

実装上は、13.1擬似コードの `collect_traits(base_stock, selected_items)` の `base_stock` が
濃度段階に応じたタグを返す形にする。鍋は「毎回必ず入る、状態が変わる具材」のように振る舞う。

#### 2.3 水: 1日の汲める量で縛る

水は無限ではない。**共用栓から有料で汲み、タンクで運ぶ1日分が上限**。昼の市場行きの際に
汲むイメージ。

世界観との一致: 九龍城砦では城砦に通じる水道管は実質1本で、上階の水は盗水で成り立っていた。
水が希少で勝手に湧かないのは、街がそうだからそうなる。ゲームバランスのための制約ではなく、
世界の物理がルールになっている。

水は3つの用途で取り合いになる。

1. **昼の仕込み**（鍋の総量を確保する）
2. **夜の維持**（煮詰まりを戻して営業を続ける）
3. **特定の客のための調整**（意図的に薄くする）

3について: 開始が適正なので「薄い」に到達する経路は水を入れた場合のみ。胃が重い客・疲労の
客には薄い鍋のほうが合うため、貴重な水を使って特定の一人のために鍋を整える判断がありうる。
水という希少資源が、量・質・気遣いの3方向に引っ張られる。

水が尽きた後の鍋は濃くなる一方になる。夜の後半に来る常連ほど煮詰まった鍋で応対することに
なり、この非対称は物語的にも使える。

#### 2.4 鍋が尽きたとき

常連に提供できる鍋が無くなった場合、以下から選択する。

- **店を閉める**（その常連に提供しない）
- **クズで薄い鍋を作って出す**（半額）
- **白湯を出す**（無料）

白湯は料理としては敗北だが、「それでも何か出したい」という店主の意思表示になる。料理成立は
FAIL相当でも、物語フラグは別の動き方をしうる（dignity / care の文脈）。

**その日の常連に提供し終わった時点で鍋が空なら閉店**。鍋が余っていればモブでもう少し稼げる。
ここに「常連に丁寧に作りすぎて鍋を使い切ると、その後のモブ収入を失う」トレードオフが生まれる。

注: クズの鍋も白湯も水を要する。水が尽きていれば選択肢は閉店のみになる。厳しいが筋は通る。
