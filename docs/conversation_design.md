# 会話（シナリオ）仕様メモ（設計）

> 状態: 設計段階・未実装。2026-08-12、Dialogic 2の標準機能と客データ/来店の仕組みを棚卸しした上で、
> 会話の構想を固めた。この文書に記録した内容はまだコードには一切反映されていない。

## 目的とビジョン

- 会話（シナリオ）を、プログラムに組み込まず読み込み型（外部データ）で持ちたい。修正を楽にするため
- コアビジョンは「客同士が勝手に話している様子を、プレイヤーが調理しながら横目で見る」。
  当初の「プレイヤーが調理しながら客と双方向に会話する」は煩わしいと判断し、この形に再定義した
- ゲーム進行と連動させたいが、複雑にはしたくない（一人開発で管理できる範囲に収める）

## 会話の2層構造

- **汎用会話**: 決まったキャラクター同士が同席している時に、ランダムで流れる「いつもの雑談」。
  プレイヤーの応答不要。発生条件は主に「同席する客の組み合わせ」（必要なら評判・日数も）。
  例: 1日目のスープ準備中、老人と配達員が同席、評判低め → 元気のない老人に配達員が
  「肉食え肉」と騒ぐ、老人は「ベースは決まってる、濃い味はつらい」と返して天気の世間話
- **特別会話**: 日時やフラグ（ストーリー進行、キャラクターの状態）に紐づいて、特定条件が揃った時
  だけ流れる会話。ストーリーを動かす場面で使う
- **選択ロジックの原則**: 特別会話の条件が合えばそれを優先、なければ同席の顔ぶれに対応する
  汎用会話をランダムに選んで流す

## 会話とプレイヤーの関係（2種類の会話）

- **自律会話（客同士）**: プレイヤーの応答不要。調理しながら横目で見る。顔ぶれ・評判・日数で内容が変わる
- **直接会話（プレイヤーと客）**: メインの客とプレイヤーが対話する。応答・選択肢がありうる

## 同席モデル（重要な土台）

想定する1日の流れ:
Aとプレイヤー対話 → スープ用意（同席者ABCが自律的に話す）→ A提供＆対話 →
次にBがメインに交代 → スープ用意（その時いる顔ぶれABC/AB/BCが話す）→ B提供＆対話 … と続く

- メインの客は1人ずつ順番に交代し、提供・評価・プレイヤーの応答という「ゲームプレイの主軸」は
  従来通り1人ずつの直列処理
- それとは別に「同席者」がいる。同席者はその時店にいる客の集合（1〜3人）。同席者は自律会話に
  登場するが、スープ提供・ステータス変化・プレイヤーの返答は発生しない（純粋に会話演出）。
  メイン対話の横で同席者が相槌やちゃちゃを入れることもあるが、演出のみ
- 客の来店・退店で同席者の顔ぶれが増減し、それが会話の変化を生む
- **設計方針**: システムの器としては複数滞在（1〜3人）を扱えるようにするが、運用の主軸は
  1人ずつのまま軽く保つ。複数同席は「ここぞ」の場面（汎用のたまの2人掛け合い、特別会話の
  2〜3人シーン）で使う

## Dialogicの活用範囲（棚卸し済み）

- 会話は Dialogic のタイムライン（`.dtl`）として外部ファイルで持てる（読み込み型の要望に直接合致）。
  `res://dialogue/` 等に配置、ビジュアルエディタでもテキストでも編集可
- `GameState` を Dialogic から直接参照可能（`{GameState.reputation}` 等）。変数の二重管理不要
- 選択肢・条件分岐、会話⇔ゲームの双方向連携（signal/do イベント）も標準機能
- どの `.dtl` を再生するか選ぶロジックは Dialogic の外（呼び出し側 GDScript）で作る＝ここが
  独自に整える部分
- 注意点: Dialogicのオートロード準備完了後でないと Autoload参照ができない制約。バージョンは
  Dialogic 2.0 Alpha 20（Godot 4.7互換は公式確認済みだがAlpha版）

## 現状のシステムとのギャップ（棚卸しで判明）

- 現状は「アクティブな客は常に1人」（`_customer_index` が1人を指す）。複数客が同時に滞在する
  「同席」の概念がシステムに存在しない。これが最大のギャップ
- 客データ（`CustomerResource`）は3人（roujin/haitatsuin/keiji）が `.tres` で存在。設計書は6人構想
- `CustomerResource` に「会話タイムライン参照」フィールドは無い。現状 `d1_roujin` が `game.gd` に
  固定でベタ書き。`hint_lines` という空Dictionaryフィールドはあるが未使用
- `DayScheduleResource.visitors` はあるが、day1〜7とも同じ3人の仮データ
- 会話発生条件に使う要素の現状: 評判(`reputation`)・日数(`day`)は `GameState` にあり参照可能。
  `story_flags` は箱だけ存在し運用ルール（どのイベントで何のキーを立てるか）未設計。
  同席の組み合わせは概念自体が無い

## 会話を実装するために必要な土台工事（次にやること）

1. **最優先: 「同席者」概念の導入。** 現状の「アクティブな客1人」を「今店にいる客の集合
   （1〜3人）＋その中のメイン1人」に拡張する。ゲームプレイの主軸（提供・評価・応答）は
   メイン1人に対して従来通り、同席者は会話演出専用。客の来店・退店で顔ぶれが増減する仕組み
2. `CustomerResource` に会話タイムライン参照の持たせ方を設計（フィールド追加か、
   `d{日}_{客id}` 規約からの動的解決か）
3. 会話の選択ロジック（特別優先→なければ汎用ランダム、顔ぶれ・評判・日数で絞る）
4. `story_flags` の運用ルール設計（特別会話の条件に使う場合）
5. 客データ・来店データの拡充（3人→6人、日ごとの実データ）

## スコープ外・後回し

- 会話本文の執筆自体は土台ができてから
- 「ながら作業」を厳密な同時滞在（複数客の立ち絵が並んで同時進行）にする大改修は、まず緩めの
  同席モデルで進め、必要なら後で検討

## 同席者モデル 具体設計（2026-08-15）

> 上記「同席モデル（重要な土台）」の方針をさらに詰め、具体的なデータ構造・選出ロジックまで
> 設計した。実装はまだ未着手（実装フェーズは「現状コードとのギャップ」節参照）。

### 1日の客処理: 2段階構造

**第1段（母集団の選出・5〜6名）**

- `story_flags` 条件を満たす「フラグ客」を優先で投入し、残りをランダムで埋めて合計5〜6名。
  この集合が「その日店にいる客（母集団）」
- 母集団選出はスキーマとしてはランタイム抽選（案T: フラグ客=確定＋ランダム枠の候補プールから
  実行時抽選）を見据えて設計する。ただし当面は客が6人と少なく母集団抽選のランダム性が
  効きにくいため、運用は母集団を固定的に定義（案S）で軽く始める。客プールが育ったら案Tへ
  移行する。スキーマに「ランダム枠の候補プール」を持てるようにしておくことで将来移行可能にする

**第2段（役割割り当て）**

- 母集団のうち3名が「メイン客」。フラグ客→ランダムの順で3枠を埋める（フラグ客が2名いる日は
  メイン=その2名＋ランダム1名、など）。メイン客は提供・評価・プレイヤー応答の対象で、従来の
  `_customer_index` による1人ずつの直列処理を踏襲する
- 残り2〜3名が「対話用客」。同席・会話演出専用で、提供・評価・応答は発生しない
- 対話用客にもフラグ指定がありうる（story上「この日は背景にこのキャラを必ず置く」等の演出を、
  客同士の会話で優先したい場合）

### 同席と会話: コンテンツ駆動の明示パターン＋重み抽選

- メイン客ごとに「同席パターン」のリストを持つ。各パターン＝「同席する顔ぶれ（例: AB, AC,
  Aのみ）」＋「抽選の重み（例: 30/30/40）」＋「その顔ぶれ用の会話バリエーション（複数の
  タイムライン候補）」
- **重要な設計原則**: 用意したパターンだけが抽選候補になる（コンテンツ駆動）。全組み合わせを
  網羅する必要はなく、「AB用の掛け合いを作ったからABが出る」「作っていない顔ぶれ(AD等)は
  出ない」。これにより母集団が広くても組み合わせが数学的に爆発せず、作業量は「作りたい
  掛け合いの数」に比例するだけ。本文書冒頭の既存方針「軽く保つ」「複数同席はここぞで使う」と一致
- 同席候補は母集団5〜6名全員（メイン客も対話用客も含む）。後でメインになる客が、先に別の
  メイン場面で同席者として出てもよい（同席とメインは独立。同席に出たかどうかはメイン登場順に
  影響しない。メイン登場順は従来通り）
- 会話選択の優先順位（既存の「特別優先→汎用ランダム」を踏襲）: そのメイン場面で
  `story_flags` 条件を満たす「特別パターン」があれば確定で使用（例: Day5の黒社会＋刑事の
  同席掛け合い）。なければ通常パターンを重み付き抽選。選ばれたパターンの会話タイムライン
  候補からさらにランダムで1本選び `Dialogic.start()` する

### データ構造の骨格（案・名称は仮）

- **CompanionPattern**（同席パターン1つ）: `companions: Array[StringName]`（同席者id、
  空=メインのみ）／ `weight: int`（抽選の重み）／ `timeline_ids: Array[StringName]`（この
  顔ぶれ用の会話タイムライン候補、複数からランダム）／ `required_flags: Array[StringName]`
  （空でなければ「特別パターン」。`story_flags` が条件を満たす時のみ通常抽選より優先）
- **CompanionScene**（1メイン場面の同席定義）: `main: StringName`（メイン客id）／
  `patterns: Array[CompanionPattern]`
- **DayScheduleResource（拡張）**: 現状の `visitors`（メイン登場順）を活かしつつ、母集団の
  定義（当面は固定リスト、将来はランダム枠候補プール）、対話用客、各メインの
  `CompanionScene` 群を持てるよう拡張する。既存の `previewed`（未使用）の扱いは今後整理

### 現状コードとのギャップ（実装フェーズで対応）

- `CustomerResource` に会話タイムライン参照フィールドが無い（現状 `CONVERSATION_TIMELINE_ID`
  は `"d1_roujin"` 固定ハードコード）。会話は同席パターン側(`timeline_ids`)で持つ設計なので、
  客リソースではなくパターン側に会話参照を置く方針
- `game.gd` は `_customer_index` 単体の直列処理で「今店にいる集合」の概念が無い。母集団・
  メイン・対話用客・同席抽選の保持と処理を追加する必要がある。メインの直列処理自体は維持
- `DayScheduleResource` の `visitors` は滞在区間の概念が無いフラットな配列。上記スキーマ
  拡張が必要
- 同席抽選のタイミング（日の開始時に一括か、各メイン場面で都度か）とセーブ/ロードでの
  同席状態の保存有無は未決。実装フェーズで判断（要検討として記録）

### 母集団・メイン選出アルゴリズム（案Tの具体仕様、実装は客プール拡充後）

- 選出は「フラグ優先 → 残りランダム」という一本の原則を、メイン枠 → 対話用枠の順に適用する

**手順:**

1. フラグ客の確定: `story_flags` により「この日メインに出る」と指定された客を、まず
   メイン枠に確定投入する（例: Day5の黒社会・刑事）
2. メイン枠をランダムで充足: メイン枠（3名）の残りを、フラグの無い客からランダムに
   選んで埋め、メイン3名を確定する
3. 対話用枠を充足: さらに残った客（フラグの有無・メイン落選を問わず）から、対話用客
   （2〜3名）を振り分ける。これで母集団（5〜6名）が揃う

**補足:**

- この「フラグ優先→残りランダム」は前回記した会話選択の優先順位（特別優先→汎用ランダム）
  と同じ思想を、客の選出にも適用したもの
- 対話用客にもフラグ指定がありうる（「この日は背景にこのキャラを必ず置く」等）。その場合は
  手順1・3でフラグを尊重する
- 母集団・メインの確定は「日の開始時」に一度だけ行う（各メイン場面での同席抽選＝別の階層
  とは区別する。下記「抽選の二層構造」参照）
- この母集団・メイン確定の結果はセーブしない。セーブは営業終了時（翌日へ）に行われ、
  ロードは常に翌日の頭からなので、日の開始時に毎回再構築される

### 抽選の二層構造（実装の基準）

同席者モデルの抽選には2つの階層があり、タイミングが異なる。

- **第1階層（母集団・メインの確定）**: 「今日来る客は誰か（母集団5〜6名）」「そのうち
  メインは誰か（3名）」「対話用は誰か（2〜3名）」。日の開始時に一度だけ確定する。上記の
  選出アルゴリズムがこれ
- **第2階層（各メイン場面の同席抽選）**: 「あるメイン客の場面で、隣に誰が同席するか」。
  各メイン場面に入る瞬間に都度抽選する（案あ）。`CompanionScene` の `patterns` から、
  特別パターン（`required_flags` 充足）優先 → なければ重み抽選で1つ選ぶ
- どちらの抽選結果もセーブしない（第1階層は日の頭で再構築、第2階層は場面ごとに都度抽選）

### 当面の実装方針（案S運用）

- 現状は客が3名（roujin/haitatsuin/keiji）のみで、母集団に入れる候補が少なく案T（実行時
  抽選）のランダム性が機能しない（抽選しても毎回同じ3名になる）。そのため当面は案S＝
  固定定義で運用する
- 案S では `day{N}.tres` に、その日の対話用客（`companions_pool`）と各メインの同席定義
  （`companion_scenes`）を直接書く。`game.gd` は書かれた通りに読むだけで、選出アルゴリズム
  （フラグ→ランダム）は実装しない
- スキーマ（データの器）は将来の案T移行を妨げない形にしておく。ただし「フラグ確定メイン」
  「ランダム候補プール」を分離するフィールドは、実際に選出ロジックを実装する将来のステップ
  で必要になってから足す（現状の客数では使い道がなく空のままになるため、先には作らない）
- 既存の `visitors`（メイン登場順3名）はそのまま「メイン客」として維持する。母集団 =
  `visitors`（メイン）＋ `companions_pool`（対話用）
