## 解決したい問題

「所持金0 ＆ ベース素材0」の状態が翌日以降も継続してしまうと、休業しても状態が変わらず
脱出不能な詰み状態になりうる。困窮の深さに応じて段階的に手段が用意されている必要がある。

## 3段階の救済構造

| 状態 | 手段 | 選択のされ方 |
|---|---|---|
| ベース在庫あり（通常） | 新しいベースで仕込み。前日の鍋（＝残り湯）も任意で選べる | プレイヤーの任意選択。残り湯を選ぶと評価・売上が下がる（質と節約のトレードオフ） |
| ベース在庫0、前日の鍋が残っている（`pot_carryover_volume > 0`） | 残り湯。前日の鍋を持ち越し、水を大量に足して薄めて使う | 実質これしか選べない状態 |
| ベース在庫0、前日の鍋もない（`pot_carryover_volume <= 0`）、かつ所持金がベース価格以下 | クズ食材（クズ野菜・臓物の切れ端）。市場で分けてもらう最終手段 | 市場（行き先選択）画面到達時に条件判定、満たせば0円で選択可能 |

## 残り湯の仕様

- 「水を足す」行為自体は営業中プレイヤー操作（`Pot.add_water`相当、少量）と残り湯作成（大量・3杯分）で同じだが、量が違う。残り湯作成では大量に足すぶん大きく薄まる
- 前日のスープが既に薄かった場合、残り湯としてさらに薄くなる（累積劣化）。この累積は「鍋を素のまま持ち越す」土台の上で自然に表現される。専用の連続使用カウンターは必須ではなくなる可能性がある（attrsの薄さ自体が劣化を表すため）。ただし「2日連続で強制的に水になる」のような明示的な閾値を入れたい場合は、別途カウンターまたは下限チェックが要る（要検討・未確定）
- 困窮時専用ではなく、ベース在庫があっても任意に選べる（質を落として節約する手段として常時選択肢に入る）

## クズ食材の仕様

- 発動タイミング: 市場（行き先選択）画面に移動した時点で判定
- 発動条件: 所持金がベース価格以下（現状のベース価格でいうと精進500円以下）**かつ** 前日の鍋の残りがない（`pot_carryover_volume <= 0`）
- 挙動: クズ野菜が0円で選択できる。所持は1個だけ

## 持ち越し判定

「前日の鍋が残っているか」は営業終了時点の `volume` で判定する。`volume > 0` なら持ち越しあり、
`volume <= 0` なら持ち越しなし。

現状は客3人構成のため、営業すれば通常`volume`は必ず残る（＝クズ食材の発動条件はほぼ満たされない）。
将来モブ客が増えてvolumeを使い切る展開が生まれた時のための仕組みとして、今のうちに用意しておく。

## 応用の実装状況（段階2・残り湯、2026-08-12完了）

- `core/pot.gd`: `add_water()` を `add_water(times: int = 1)` に一般化。1回分の効果
  （volume+2, rich-2, umami-1、下限0ガード）を times 回重ねる形。既存呼び出し
  （`debug_pot.gd` / `test_pot.gd`）は引数省略のまま無改造で動作
- `night/game.gd`:
  - 旧 `base_zanryu.tres` ベースの固定残り湯（`ZANRYU_BASE` / `_zanryu_available()`）を廃止
  - `_build_zanryu_option()` を新設。`GameState.pot_carryover_*` の値を持った `RecipeResource`
    （`id = &"zanryu_carryover"`）を動的に組み立て、`pot_carryover_volume > 0` の日だけ
    `_bases` に混ぜる。通常ベースと同じ選択UI（`%BtnSelectBase`）でそのまま任意選択できる
  - `_on_setup()`: 選択されたのが残り湯（`id == ZANRYU_CARRYOVER_ID`）なら、`Pot.setup()`で
    持ち越し値を復元した直後に `add_water(ZANRYU_WATER_TIMES)` で希釈する
  - 希釈量は `ZANRYU_WATER_TIMES = 2` の仮値。客3人前提のバランス値で、実機確認しながら調整予定
  - 在庫ベースも持ち越しの残り湯も無い日は、段階3（クズ食材）が未実装のため暫定的に

- `scenes/market/destination_select.gd` / `DestinationSelect.tscn`: 旧残り湯の固定表示
  （`%LabelZanryu`）を削除。残り湯の数値は仕込み画面の選択肢上で確認できるため、
  行き先選択画面に別途表示する必要が無くなった
- `data/recipes/base/base_zanryu.tres`: ファイル削除。パス参照・uid参照とも
  プロジェクト内に残っていないことを確認済み
- 未実装だった段階3（クズ食材）は後日実装完了（「段階3の実装状況」参照）。累積劣化の
  明示的な閾値（下限0ガードは `add_water`に既存だが、「2日連続で強制的に水になる」的な

## 段階3の実装状況（クズ食材、2026-08-13完了）

3段構造（通常/残り湯/クズ食材）が出揃い、困窮脱出動線がひとまず完成した。

- **入手経路**: 「クズ食材の仕様」の当初案は行き先選択画面での判定だったが、実装は
  市場シーン（`Shop.tscn`）内の「裏手」ボタン（`%BtnAlley`）に置いた。市場に入って
  はじめて条件判定・入手ができる（行き先選択画面自体には手を入れていない）
- **発動条件**（`shop.gd::_is_junk_available()`）: 以下4条件のAND
  1. `GameState.money < _cheapest_base_price()` … 最安ベースすら買うのに所持金が足りない
     （当初案は「ベース価格以下」だったが、ちょうど買える金額なら買えるはずなので `<` に
     厳密化した）
  2. `not _has_base_in_inventory()` … 通常ベースを1個も持っていない（新設。`_bases` を
     inventoryでフィルタして判定。`night/game.gd` の在庫フィルタと同じ考え方）
  3. `GameState.pot_carryover_volume <= 0` … 残り湯（前日の鍋の持ち越し）も無い
  4. `not GameState.junk_taken_today` … その日まだ拾っていない（「所持は1個だけ」という
     当初案を、日替わりで再取得できる形で具体化した）

  最安ベース価格は `_cheapest_base_price()` が `_bases` を走査して動的に求める
  （ハードコードしない）。将来ベースの価格・種類が変わっても追従する
- **入手処理**: 条件を満たす時だけ裏手ボタンが表示され、押すと `base_kuzu` を
  `GameState.inventory` に0円で1個加算し、`junk_taken_today` を立てる
- **当日1個制限の仕組み**: `GameState.junk_taken_today` / `junk_reset_day` の2フィールドで
  日替わりリセットを実現する。`junk_reset_day != GameState.day` を `shop.gd::_refresh()`
  冒頭（`_refresh_junk_day_guard()`）で評価し、不一致なら `junk_taken_today = false` と
  `junk_reset_day = GameState.day` を書き込む。市場に同日再入場してもリセットされない
  （将来、薬味屋・水汲み場など市場以外の場所を経由しても day が変わらない限り保持される
  設計）。両フィールドともセーブ対象外（`SaveManager` は明示列挙方式のため何もしなくても
  自動では混入しない）。ロードは基本「翌日の頭」で発生し、その時点で `junk_reset_day`
  （save.jsonに無いので初期値0）と `GameState.day` が不一致になるため、次に市場でガードを
  評価した時点で自然に `junk_taken_today = false` に戻る
- **夜営業での扱い**: `base_kuzu.tres`（`Kind = BASE`）を `night/game.gd` の
  `_base_catalog` に追加。既存の `inventory` フィルタ（`_bases = _base_catalog.filter(...)`）
  がそのまま効くため、クズ食材を持っている日だけベース選択肢に出る。残り湯のような
  専用の仮想 `RecipeResource` 生成（`_build_zanryu_option()`）は不要で、通常ベースと
  同じレールに乗る
- **attrsの暫定値**: `base_kuzu.tres` の `attrs` は `rich=1 / light=1 / umami=0`
  （通常ベースの豚骨 `rich=5` ・精進 `light=5` より明確に貧相な値）。粗末さの表現として
  暫定的に決めたもので、「味の数値スケール設計」（本ドキュメント末尾の派生検討課題）の
  フェーズで見直す予定
- **Godotの落とし穴**: `base_kuzu.tres` 本文には当初「暫定値であることを示すコメント」を
  `;` 行で書いていたが、`night/game.gd` が `preload` で参照するようになった後にエディタで
  プロジェクトを開く（フルスキャンが走る）と、Godotが未採番だった `uid` を割り当てるために
  リソースを再シリアライズし、このカスタムコメントと（デフォルト値と一致する）`price = 0`
  の明示行が消えた。`.tres`（テキストリソース）はGodotに一度でも保存し直されるとカスタム
  コメントを保持しない仕様と考えられる。**設計意図を記録したい場合は `.tres` 本文の
  コメントを当てにせず、このドキュメント側に書く**（上のattrs暫定値の説明がその実例）
- **実機確認**: 市場側（裏手ボタンの表示条件・0円入手・入手後に消える）、夜営業側
  （クズ食材のみが選択肢に出る・仕込み・提供・評価が既存 `Evaluator` にそのまま乗る）
  とも確認済み

**保留・次の一手**

- attrs暫定値（`rich=1/light=1/umami=0`）は「味の数値スケール設計」フェーズでの見直し対象
- 裏手ボタンのレイアウト・文言は仮（`Shop.tscn` に `VBoxContainer` の子として仮配置。
  見た目の調整はM5ポリッシュ工程）
- クズ食材の会話・reputationへの反映（「クズ食材で凌いだ」ことを客が言及する等）は
  会話全面改訂フェーズ（`docs/conversation_design.md`）で扱う候補

## 将来の夜営業拡張との関係（前提として関連する構想）

- 客は「訪れる客」（会話あり、味付け・評価あり）と「モブ客」（提供のみ、鍋の量と売上に反映）の
  2種になる予定
- 営業中は水（薄める）だけでなくベースも足せるようになる予定（濃さを戻す、在庫を消費する）。
  営業終了時点の鍋の濃さは濃い〜薄いまで幅を持つことになる
- 水の量（残り湯3杯・営業中2杯程度）は現状の客3人前提の仮の数字。客数が変わったら見直しが要る

## 既存の負債（2026-08-12解消）

旧 `base_zanryu.tres` ベースの「残り湯」実装（`night/game.gd`）は、本構想の残り湯とは別物だった。

- その日限りの固定の薄いベース（.tresに固定値、日をまたぐ状態を持たない）
- ベース在庫0のとき自動代入されるだけで、プレイヤーが任意に選ぶUIが無い
- 連続使用による劣化が無い

応用（段階2）の実装に伴い、この旧実装は廃止し新しい残り湯に一本化した（「応用の実装状況」参照）。

## 派生した検討課題（未着手・別課題）

残り湯（段階2）の設計を詰める過程で見えた、残り湯単独のスコープを超える課題。実装は後日、

### 味の数値スケール設計

`SoupAttrs`（rich/light/umami）は現状 int で、レンジが小さい。レンジが小さいと1回の水/ベースの
効果が相対的に大きく、細かい調整がしづらい。将来、数値スケールを大きく取ることで整数のまま
繊細な味調整を可能にする案がある。

これは残り湯単独の課題ではなく、客の `ideal`・評価閾値（`great_threshold`/`ok_threshold`）・
煮詰まり（`on_turn_end`）・ベース・トッピング・薬味すべてに関わる「味システム全体の解像度設計」。
独立した「味のバランス設計」課題として、客データ拡充後などにまとめて扱う。

小数化（float）は影響が大きく採らない方針。スケールを上げる方向で検討する。

### 「ベース（またはベースの材料）を足す」操作（将来仕様）

営業中、水を足す（薄める、rich/umami↓ volume↑）とは別に、ベースを足して味を濃く戻す
（rich/umami↑）操作を予定する。水と対になる操作。

今回の `add_water(times)` 一般化と同じ構造で、将来 `add_base` 相当を足せる想定。今日は
実装しないが、設計として見込んでおく。
